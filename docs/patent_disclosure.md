# Lyra Patent Disclosure Draft

作成日: 2026-06-11  
対象: Lyra の漫画生成支援パイプライン  
用途: 自力で特許出願書類を作成するための発明整理・明細書・請求項・要約書素材  
公開可否: 出願前は非公開推奨

## 0. この資料の位置づけ

本資料は、Lyra の中核パイプラインについて、特許出願書類を自力で作成するための発明整理資料である。

目的は、単なる「AIで漫画を作る」一般論ではなく、以下の具体的な情報処理を権利化候補として整理することである。

- 物語情報をページ単位およびコマ単位へ分配する。
- 各コマについて、登場人物、状況、背景、構図、カメラアングル、セリフ、話者を含む編集可能な構造化データを生成する。
- キャラクター名、別名、参照画像、entity ID を用いて、登場人物の一貫性を保つ。
- LLM 出力が形式上正しくても内容が薄い場合に、項目単位で検査・補完する。
- 構造化データ、キャラクター参照画像、レイアウト情報を統合し、画像生成モデル用プロンプトへ変換する。
- 変換後のプロンプトが必要情報を欠落していないか検査し、必要に応じて安全な下書きプロンプトへ戻す。

本資料は法的助言ではない。弁理士を使わない前提で、出願人本人が願書、明細書、特許請求の範囲、要約書、図面を作成するための作業台として用いる。最終提出前には、少なくとも特許庁の最新様式、手数料、審査請求期限、電子出願手続、先行技術調査結果を確認する。

## 0.1 出願上の本命

本資料では、出願時の主軸を以下へ寄せる。

```text
LLM と画像生成モデルの間に配置される、漫画ページ生成用の制約保持・欠落検査・項目補完・fallback パイプライン
```

広い「物語から漫画を作る」発明は、脚本からストーリーボードを作る技術、AI storyboard generation、frame-by-frame constraints、画像生成用プロンプト生成技術と衝突しやすい。したがって、独立請求項では、単なる story to comic ではなく、以下を中核に置く。

- コマ単位の構造化情報を保持する。
- セリフ話者、セリフ文面、登場人物、視覚制約を必須制約ブロックとして生成する。
- 決定論的に生成した第一プロンプトを、LLM により第二プロンプトへ整形する。
- 第二プロンプトに必須制約ブロックの情報が残っているかを検査する。
- 欠落がある場合、第二プロンプトを採用せず、第一プロンプトまたは補完後プロンプトへ fallback する。

この主軸により、発明を「AI漫画生成」ではなく、「LLM 出力の不安定性を漫画制作パイプライン内で制御する具体的な情報処理」として説明する。

## 1. 発明の名称候補

第一候補:

```text
漫画ページ生成用プロンプト生成システム
```

この名称に絞る。広い「漫画生成支援システム」や「物語情報から漫画ページ生成用構造化データを生成するシステム」は、本命の欠落検査・fallbackから焦点がずれるため、初回出願では使わない。

請求項内では、プロンプトコンパイル、コマ単位構造化、必須制約ブロック、欠落検査、項目補完、参照画像対応付け、fallback を限定する。

## 2. 発明の要約案

本発明は、漫画ページ生成用プロンプトを生成する情報処理システムに関する。システムは、物語情報、登場人物情報、登場人物の参照画像、及びコマ単位の編集情報を取得し、物語情報をページ単位及びコマ単位へ分配する。各コマ単位情報には、登場人物識別子、状況、背景、構図、カメラアングル、セリフ、セリフ話者、及び視覚制約情報が含まれる。システムは、登場人物名及び別名を正規化された登場人物識別子へ対応付け、コマ単位情報からセリフ制約及び視覚制約を含む必須制約ブロックを生成し、当該必須制約ブロックを含む第一プロンプトを生成する。さらに、第一プロンプトの少なくとも一部を言語モデルにより整形して第二プロンプトを生成し、第二プロンプトに必須制約ブロックに対応する情報が保持されているかを検査する。欠落が検出された場合、第二プロンプトではなく第一プロンプト又は補完後プロンプトを画像生成モデルへ入力する。

## 3. 技術分野

本発明は、AI を用いた創作支援、漫画制作支援、画像生成支援、自然言語処理、プロンプト生成、構造化データ生成、及び画像生成モデルへの入力制御を行う情報処理システムに関する。

より具体的には、ユーザーが入力した物語、章、話、シーン、キャラクター情報を、漫画制作に適したページ単位およびコマ単位の構造化データに変換し、当該構造化データとキャラクター参照画像とを用いて画像生成モデル用プロンプトを生成する情報処理技術に関する。

## 4. 背景技術

近年、テキストから画像を生成する画像生成モデル、および文章生成を行う大規模言語モデルが普及している。これにより、ユーザーは自然言語で指示を入力することで、イラスト、漫画風画像、キャラクター画像などを生成できる。

しかし、漫画制作では単一画像の生成とは異なり、以下の情報を同時に制御する必要がある。

- ストーリー全体の進行
- 章、話、ページ、コマの階層構造
- ページごとの役割
- コマごとの状況、背景、構図、カメラアングル
- コマごとに登場するキャラクター
- キャラクターの表情、姿勢、位置、向き
- セリフ、話者、ナレーション
- キャラクター外見の一貫性
- コマ割りレイアウトの一貫性

従来の単純なプロンプト入力方式では、ユーザーが画像生成モデルに直接長文プロンプトを書く必要がある。また、ストーリー全体をそのまま画像生成モデルへ渡すと、ページごとの情報配分、コマごとの役割、登場人物の選定、構図、セリフが不安定になりやすい。

また、LLM に JSON などの構造化出力を求める場合でも、形式上は妥当な JSON が返ってきても、内容が薄い、同じ説明が各コマに繰り返される、キャラクター割り当てが空になる、セリフの話者が欠落する、構図やカメラ情報が欠落する、といった問題が生じる。

さらに、キャラクターの一貫性を保つには、単なる名前や文章説明だけでは不十分であり、参照画像、キャラクター識別子、別名、コマごとの登場情報を整合させる必要がある。

なお、脚本からストーリーボードを生成する技術、AI による storyboard generation、フレーム単位のユーザー制約を扱う技術、画像生成用プロンプトを生成する技術は既に存在する可能性が高い。したがって、本発明では、広い「物語から漫画を作る」処理自体ではなく、LLM による構造化出力及びプロンプト整形において、漫画ページ生成に必要なコマ単位制約が欠落する問題を検査、補完、及び fallback により制御する点を重視する。

## 5. 解決しようとする課題

本発明が解決しようとする主な課題は以下である。

1. ユーザーがプロンプトを書かなくても、物語から漫画ページを生成できるようにする。
2. 物語全体を、指定されたページ数および各ページのコマ数へ自然に分配する。
3. 各コマに必要な情報を、状況、登場人物、背景、構図、カメラアングル、セリフ、話者として分離して扱う。
4. LLM の出力が形式的に正しくても内容が不足している場合に、生成前に検査・補完する。
5. キャラクター名、別名、参照画像、entity ID を用いて、コマごとのキャラクター割り当てを安定させる。
6. 画像生成モデルへ渡す最終プロンプトに、コマごとの必須情報が欠落しないようにする。
7. 漫画制作者が後から編集できる中間データを保持し、単なる一発生成ではなく制作パイプラインとして扱えるようにする。
8. LLM が第一プロンプトを自然言語の第二プロンプトへ整形する過程で、セリフ話者、セリフ文面、登場人物、視覚制約、参照画像対応が失われる問題を検出する。
9. 第二プロンプトに必須制約が保持されていない場合、当該第二プロンプトを採用せず、決定論的な第一プロンプト又は補完後プロンプトへ切り替える。
10. 既存の storyboard 生成技術との差異として、漫画ページ生成に必要なコマ単位制約の保持と、コンパイル後の欠落検査を具体的な情報処理として実現する。

## 6. 発明の基本構成

本発明の漫画生成支援システムは、少なくとも以下の構成要素を備える。

### 6.1 入力取得部

以下の少なくとも一部を取得する。

- 作品情報
- 章情報
- 話情報
- 物語本文
- シーン情報
- 生成対象ページ数
- ページごとのコマ数またはコマ割りテンプレート
- 登場人物情報
- 登場人物の別名情報
- 登場人物の参照画像
- コマごとの既存編集情報
- ユーザーが選択した言語

### 6.2 物語分配部

物語情報を、生成対象ページ数に応じてページ単位の物語単位へ分配する。

実装上は、序盤、中盤、クライマックス、終盤などの分割入力または全体入力を受け取り、文・段落・節を抽出し、ページ数に応じて分配する。

### 6.3 ページ計画部

各ページについて、以下を生成または保持する。

- ページ番号
- ページの目的
- 継続性メモ
- 由来シーン ID
- 推奨コマ数
- 推奨レイアウト
- ページ全体のセリフモード

### 6.4 コマ分割部

各ページの物語単位を、ページ内の複数コマへ分割する。各コマは読順に沿って配置される。

各コマについて、以下のような役割を割り当てる。

- 導入
- 行動
- 反応
- 強調
- 転換
- 間
- 衝撃

### 6.5 コマ構造化部

各コマについて、漫画制作に必要な編集可能フィールドを生成する。

代表的なフィールド:

- 状況テキスト
- コマ役割
- コマサイズ
- 構図ソース
- 構図プロンプト
- ショット種別
- カメラアングル
- カスタム演出メモ
- 背景メモ
- 効果音
- セリフ
- セリフタイプ
- セリフ話者
- セリフ位置
- 登場人物割り当て
- 登場人物の役割
- 表情
- アクション
- 画面内位置
- 向き
- 演出効果

### 6.6 登場人物正規化部

登場人物の名前および別名を用いて、物語本文やシーン本文に現れる表記を正規の登場人物識別子へ対応付ける。

特徴:

- 正規名と別名を mention index として扱う。
- 長い別名を優先して照合する。
- 同じ別名が複数キャラクターに共有される場合は曖昧な照合として除外する。
- 保存済みの物語本文は書き換えず、コンパイラへ渡す brief や fallback inference のみ正規化する。
- コマごとの visible subject を決定し、全キャラクターを全コマへ機械的に割り当てない。

### 6.7 品質検査部

LLM または規則ベース処理により生成された構造化データについて、以下を検査する。

- ページ数が指定ページ数と一致するか。
- ページ番号が連続しているか。
- コマ数がレイアウトテンプレートと一致するか。
- コマ順が連続しているか。
- コマごとの登場人物 ID が許可された範囲内か。
- コマごとの登場人物が重複していないか。
- 状況、構図、カメラ、背景、登場人物、セリフなどの編集可能フィールドが過度に空でないか。
- 同じ文章が状況、構図、背景などへ重複して入っていないか。
- generic な文言のみで実質的な情報がないか。
- セリフがある場合、話者またはナレーション種別が適切か。

### 6.8 項目単位補完部

検査により不足が検出された場合、全体を破棄するのではなく、項目単位で補完する。

補完例:

- 登場人物が空の場合、ページ目的、シーン、物語本文、別名情報から候補を推定する。
- 構図が空の場合、コマ役割からショット種別とカメラアングルを補う。
- 背景が空の場合、シーンの場所、時間、雰囲気から補う。
- セリフが空の場合、必要に応じてナレーション、思考、短い会話を補う。
- 同じ説明が複数フィールドに入っている場合、状況、構図、背景の役割に応じて分離する。

### 6.9 プロンプト構築部

ページおよびコマの構造化データ、キャラクター参照画像、レイアウト情報を統合し、画像生成モデル用プロンプトを構築する。

プロンプトには以下が含まれる。

- ページ全体の目的
- 参照画像の役割
- キャラクター参照画像とキャラクター名の対応
- コマ割りレイアウト指示
- コマごとの状況
- コマごとの登場人物
- コマごとの構図
- コマごとのカメラアングル
- コマごとの背景
- コマごとのセリフ、話者、ナレーション指定
- 画風またはスタイル制約
- ネガティブ制約

本資料では、構造化データから決定論的に生成されるプロンプトを「第一プロンプト」又は draft prompt と呼ぶ。第一プロンプトは、LLM の自由な要約や推論に依存せず、保存済みのコマ構造化情報から組み立てられる。

### 6.10 ロック情報生成部

プロンプト内に、コマごとの必須制約を明示するロック情報を生成する。

Dialogue lock:

- セリフ文面
- 話者
- ナレーションかキャラクター発話か
- セリフの省略、改変、統合、分割、話者変更の禁止

Visual lock:

- コマ番号
- コマに登場するキャラクター名
- ショット種別
- カメラアングル
- 背景 cue

本資料では、Dialogue lock 及び Visual lock を含む、コマ単位で保持すべき制約のまとまりを「必須制約ブロック」と呼ぶ。

### 6.11 コンパイル後検査部

画像生成モデル用の自然言語プロンプトを LLM で整形した後、Dialogue lock および Visual lock が欠落していないか検査する。

LLM により整形されたプロンプトを「第二プロンプト」又は compiled prompt と呼ぶ。検査部は、第二プロンプトに、第一プロンプト又は必須制約ブロックに含まれる以下の情報の少なくとも一部が保持されているかを検査する。

- コマ番号
- 登場人物識別子に対応する登場人物名
- 参照画像と登場人物の対応
- セリフ文面
- セリフ話者
- ナレーション種別
- ショット種別
- カメラアングル
- 背景 cue

欠落が検出された場合は、LLM が整形したプロンプトを採用せず、決定論的に構築された draft prompt を使用する。

検査部は、単に人間が目視確認するのではなく、コンピュータにより以下の処理を実行する。

1. 必須制約ブロックから、検査対象となるキー情報を抽出する。
2. 第二プロンプトから、キー情報に対応する文字列、識別子、又は正規化済み表現を抽出する。
3. 抽出した情報を、完全一致、正規化一致、対応テーブル、又は所定の類似度判定により照合する。
4. 照合結果が所定条件を満たさない場合、第二プロンプトに欠落があると判定する。
5. 欠落の種類に応じて、第一プロンプトを採用するか、第二プロンプトへ不足情報を追加した補完後プロンプトを採用する。

検査対象となるキー情報の例:

- `panel_order` 又はコマ番号
- `entity_id`
- `entity_name`
- `reference_image_id` 又は入力画像番号
- `dialogue.text`
- `dialogue.speaker_entity_id`
- `dialogue.type`
- `shot_type`
- `camera_angle`
- `background_cue`

正規化の例:

- 全角半角の統一
- 大文字小文字の統一
- 空白、句読点、引用符の除去又は統一
- `closeup` と `close_up` などの同義表記の対応
- 登場人物識別子と登場人物名の対応
- 参照画像識別子と画像番号の対応

欠落ありと判定する条件の例:

- コマ番号に対応する記述が第二プロンプトに存在しない。
- セリフ文面が完全一致又は所定類似度以上で存在しない。
- セリフ話者名又は話者識別子が、当該セリフと対応付けられていない。
- 登場人物名又は参照画像識別情報が、該当コマに対応付けられていない。
- `shot_type`、`camera_angle`、`background_cue` のうち所定数以上が欠落している。
- 参照画像と登場人物との対応が第二プロンプト内で逆転又は消失している。

### 6.12 プロンプト切替部

プロンプト切替部は、第二プロンプトの検査結果に基づいて、画像生成モデルへ入力するプロンプトを決定する。

- 第二プロンプトが必須制約を保持している場合、第二プロンプトを採用する。
- 第二プロンプトが必須制約を欠落させている場合、第一プロンプトを採用する。
- 必要に応じて、不足項目を補完した補完後プロンプトを採用する。

この切替により、LLM による自然言語整形の利点を利用しつつ、漫画ページ生成に必要な制約が失われるリスクを抑える。

### 6.13 画像生成連携部

画像生成モデルに対して、以下を入力として渡す。

- 画像生成モデル用プロンプト
- キャラクター参照画像
- 必要に応じてコマ割りレイアウト参照画像

生成結果はページ単位の漫画画像として保存される。

## 7. Lyra 実装における対応箇所

## 8. 発明の効果

本発明により、以下の効果が得られる。

1. ユーザーは画像生成用の長文プロンプトを書かずに、漫画ページを生成できる。
2. 物語全体が、指定ページ数とコマ数に応じて段階的に分配される。
3. 各コマに必要な情報が編集可能な構造化データとして保存されるため、ユーザーが生成前に確認・修正できる。
4. LLM 出力の形式的妥当性だけでなく、漫画生成に必要な情報量を検査できる。
5. 欠落がある場合に全体を破棄せず、項目単位で補完できる。
6. キャラクター名、別名、参照画像、識別子を組み合わせることで、登場人物の割り当てと外見一貫性を高められる。
7. セリフの話者、ナレーション、構図、カメラ、背景が画像生成プロンプトから欠落するリスクを低減できる。
8. 画像生成モデルへの入力が、単なる自然言語ではなく、漫画制作に必要な階層的情報から生成されるため、生成結果の安定性が向上する。

## 9. 従来技術との差異として主張したい点

強調すべき差異:

- 単に LLM に「漫画を作って」と依頼するのではなく、物語をページ、コマ、編集フィールド、必須制約ブロックに段階分解する。
- 生成結果を即座に画像へ渡すのではなく、ユーザー編集可能な構造化データとして保存する。
- 各コマについて、状況、登場人物、背景、構図、カメラ、セリフ、話者を別フィールドとして扱う。
- キャラクター参照画像と entity ID を最終プロンプトに対応付ける。
- LLM 出力の JSON が schema valid でも、情報が薄ければ field-level repair する。
- Dialogue lock と Visual lock を生成し、プロンプト整形後に欠落検査する。
- LLM により整形された compiled prompt が必須制約を落とした場合、compiled prompt を採用せず、決定論的な draft prompt 又は補完後プロンプトへ切り替える。
- 最終的な画像生成プロンプトを、構造化データ、参照画像、レイアウト、セリフ制約から構築する。

弱くなりやすい主張:

- AI で漫画を作る。
- プロンプトを自動生成する。
- ストーリーからセリフを作る。
- キャラ画像を参照する。

これらは広すぎるため、請求項では具体的な情報処理手順、データ構造、検査、補完、参照画像対応付けを含める。

先行技術との差異として特に押し出すべき点は、storyboard 生成そのものではない。既存技術が脚本からフレーム、シーン、キャラクター説明、画像又は storyboard を生成する場合でも、本発明では、LLM によるプロンプト整形後の欠落を、コマ単位の必須制約ブロックに基づいて検査し、欠落時に採用プロンプトを切り替える点を重視する。

審査上の説明では、以下を曖昧にしない。

- 何を必須情報として保持するか。
- どの単位で検査するか。
- どの ID、フィールド、制約情報を比較するか。
- どの条件で compiled prompt を破棄するか。
- どの情報を保持したまま、どの項目だけ補完するか。
- 参照画像と entity ID をどのように対応付けるか。

## 12. 追加実施例

### 12.1 失敗例と解決例

以下は、本発明が解決する典型的な失敗例である。

失敗例:

```text
LLM が 4 コマ漫画用の JSON を返した。
JSON schema は通過したが、3 コマ目の登場人物 ID が空だった。
2 コマ目のセリフは character speech として生成されたが、speaker_entity_id が未設定だった。
プロンプト compiler による自然言語整形後、4 コマ目の Visual lock が compiled prompt から消失した。
```

解決例:

```text
schema validation 後に field-level quality gate を実行する。
3 コマ目の登場人物 ID は、由来シーン、ページ目的、別名 index、及び前後コマの visible subject から補完する。
2 コマ目のセリフ話者は、dialogue type と当該コマの visible subject から補完する。
compiled prompt 検査で 4 コマ目の Visual lock 欠落を検出する。
第二プロンプトを破棄し、必須制約ブロックを含む第一プロンプト又は補完後プロンプトを画像生成モデルへ入力する。
```

この実施例により、LLM が形式上は正しい出力を返した場合でも、漫画生成に必要な制約が欠落したまま画像生成に進むことを抑制できる。

### 12.2 データ構造例

コマ構造化情報の例:

```json
{
  "panel_id": "p03",
  "panel_order": 3,
  "visible_entities": ["char_mio"],
  "situation_text": "澪が夜のホームで足を止め、遠くの光に気づく。",
  "composition": {
    "shot_type": "close_up",
    "camera_angle": "low_angle",
    "composition_prompt": "澪の横顔を大きく取り、背後に夜の駅ホームを細く見せる。"
  },
  "background_note": "night_station_platform",
  "dialogue": [
    {
      "speaker_entity_id": "char_mio",
      "type": "speech",
      "text": "まだ間に合う"
    }
  ],
  "visual_lock": {
    "subjects": ["char_mio"],
    "shot_type": "close_up",
    "camera_angle": "low_angle",
    "background_cue": "night_station_platform"
  },
  "dialogue_lock": {
    "line_order": 1,
    "speaker_entity_id": "char_mio",
    "text": "まだ間に合う",
    "type": "speech"
  }
}
```

第一プロンプトに含まれる必須制約ブロックの例:

```text
Panel 3 visual lock:
subjects=澪; shot=close_up; angle=low_angle; background cue=night_station_platform.

Panel 3 dialogue lock:
line 1 must stay assigned to 澪 exactly as written: "まだ間に合う".
Do not omit, paraphrase, merge, split, or reassign this line.
```

第二プロンプト検査の例:

```text
検査対象:
- "Panel 3"
- "澪"
- "close_up"
- "low_angle"
- "night_station_platform"
- "まだ間に合う"

判定:
いずれかが欠落している場合、第二プロンプトを不採用とする。
```

第二プロンプトの失敗例:

```text
Panel 3 shows Mio at a train station, looking determined as the night air surrounds her.
```

欠落内容:

- セリフ「まだ間に合う」が存在しない。
- `low_angle` に対応するカメラ角度が存在しない。
- `night_station_platform` が単なる `train station` に一般化されている。
- 参照画像に対応する澪の identity anchor が明示されていない。

判定例:

```text
Dialogue lock のセリフ文面が欠落している。
Visual lock の camera_angle が欠落している。
background_cue が正規化一致又は対応テーブル一致しない。
したがって第二プロンプトを不採用とし、第一プロンプト又は補完後プロンプトを画像生成モデルへ入力する。
```

### 12.3 評価設計例

出願明細書に数値が必須ではないが、技術的効果を説明するため、以下の評価設計を用意できる。

| 評価項目 | 比較対象 | 測定例 |
|---|---|---|
| セリフ話者欠落率 | Dialogue lock なし / あり | 生成前プロンプト内で話者が保持されている割合 |
| 視覚制約欠落率 | Visual lock なし / あり | compiled prompt 内で shot、angle、background cue が保持されている割合 |
| キャラクター混同率 | entity ID 対応なし / あり | コマ内の intended subject と出力プロンプト上の subject の一致率 |
| 再生成回数 | field-level repair なし / あり | ユーザーが満足するまでの平均再生成回数 |
| 編集欄充足率 | schema validation のみ / quality gate あり | situation、composition、background、entities、dialogue の非空かつ非汎用率 |

明細書に記載する場合の表現例:

```text
本実施形態によれば、言語モデルによるプロンプト整形後に、セリフ話者、視覚制約、及び登場人物参照情報が欠落したプロンプトを検出できる。そのため、欠落したプロンプトを画像生成モデルへ入力することを抑制でき、ユーザーによる再生成又は手修正の負担を低減できる。
```

### 12.4 審査で説明しやすい技術的効果

本発明の効果は、単に「漫画が作りやすい」ことではなく、以下の技術的効果として説明する。

- LLM による構造化出力が schema valid でも内容不足となる問題を、項目単位検査で検出できる。
- プロンプト整形により、セリフ話者、視覚制約、参照画像対応が欠落する問題を検出できる。
- 欠落検出時に、決定論的に生成された第一プロンプトへ切り替えることで、画像生成モデルへ不完全なプロンプトが入力されることを抑制できる。
- 登場人物識別子と参照画像を対応付けることで、キャラクター混同を抑制できる。
- コマごとの必須制約を保持することで、ページ単位画像生成におけるコマ間の情報落ちを抑制できる。

## 13. 図面案

### 図1: 全体システム構成

構成:

- ユーザー端末
- Web UI
- API サーバー
- DB
- LLM コンパイラ
- 画像生成モデル
- 画像ストレージ

流れ:

```text
ユーザー入力
  -> API サーバー
  -> 物語/キャラ/ページ/コマ DB
  -> LLM コンパイラ
  -> 構造化データ
  -> 品質検査・補完
  -> プロンプト生成
  -> 画像生成モデル
  -> 生成画像保存
  -> UI 表示
```

### 図2: 物語からページ・コマへの変換フロー

```text
物語情報
  -> 文/段落/シーン単位の抽出
  -> ページ単位への分配
  -> ページ目的・継続性情報の生成
  -> コマ単位への分割
  -> コマ役割の付与
  -> コマ構造化情報の生成
```

### 図3: 登場人物正規化フロー

```text
登場人物情報
  -> 正規名 + 別名リスト
  -> mention index 生成
  -> 物語/シーン/コマ本文との照合
  -> entity ID への対応付け
  -> コマごとの visible subject 決定
```

### 図4: 品質検査・補完フロー

```text
LLM 構造化出力
  -> schema 検査
  -> ページ数/コマ数/順序検査
  -> 登場人物 ID 検査
  -> field-level quality gate
  -> 不足項目の補完
  -> 保存
```

### 図5: 第一/第二プロンプトと lock 検査

```text
コマ構造化情報 + 参照画像 + レイアウト
  -> 第一プロンプト / draft prompt
  -> LLM prompt compiler
  -> 第二プロンプト / compiled prompt
  -> 必須制約ブロック / dialogue lock / visual lock 検査
  -> OK: 第二プロンプト採用
  -> NG: 第一プロンプト又は補完後プロンプト採用
  -> 画像生成モデル
```

| 物語情報 | 作品、章、話、シーン、またはユーザーが入力したストーリー本文 |
| ページ単位情報 | 1ページ分に割り当てられた物語の一部、ページ目的、継続性メモなど |
| コマ単位情報 | 1コマ分の状況、登場人物、構図、背景、セリフなどの情報 |
| コマ構造化情報 | 編集可能なフィールドとして保存されたコマ単位情報 |
| 登場人物識別子 | キャラクターまたはエンティティを一意に示す ID |
| 参照画像 | 登場人物の外見一貫性を保つための画像 |
| プロンプトコンパイル | 構造化データから画像生成モデル用プロンプトへ変換する処理 |
| 第一プロンプト | コマ構造化情報から決定論的に生成される draft prompt |
| 第二プロンプト | 第一プロンプト又は compiler brief を LLM により自然言語整形した compiled prompt |
| 必須制約ブロック | コマごとに保持すべき登場人物、セリフ、話者、視覚制約などのまとまり |
| Dialogue lock | セリフ文面、話者、ナレーション種別を保持する制約 |
| Visual lock | コマごとの登場人物、ショット、角度、背景 cue を保持する制約 |
| field-level repair | 出力全体ではなく、不足している項目単位で補完する処理 |

## 15. 実施形態の詳細

### 15.1 入力

ユーザーは Web UI を通じて、作品、章、話、物語本文、キャラクター情報、キャラクター参照画像、ページ数を入力する。

物語本文は、全体入力でも、序盤、中盤、クライマックス、終盤などの分割入力でもよい。

キャラクター情報には、名称、別名、自由記述、構造化フィールド、参照画像を含めることができる。

### 15.2 ページ骨格生成

システムは、指定ページ数に応じて、物語をページ単位に分配する。

ページごとに以下を生成する。

- ページ番号
- ページ目的
- 推奨コマ数
- 推奨レイアウト
- コマごとの役割
- コマごとの状況ヒント
- コマごとの推奨登場人物
- コマごとのセリフヒント

この段階では、画像生成は行わず、編集可能な骨格データとして保存する。

### 15.3 話全体からページ入力欄への自動反映

既存ページと既存コマがある場合、システムは話全体の物語情報とシーン情報を参照し、各ページおよび各コマの編集欄を自動入力する。

ページ単位では、由来シーン、ページ目的、継続性メモを設定する。

コマ単位では、状況、構図、ショット、カメラアングル、背景、登場人物、表情、行動、セリフ、話者などを設定する。

### 15.4 一ページ単体の自動入力

ユーザーが単一ページについてシーンから自動入力を実行する場合、システムは当該ページのページ番号、コマ数、既存のコマ情報、シーン情報を参照し、当該ページ内の各コマに必要な情報を補う。

### 15.5 LLM 出力の structured validation

システムは LLM に対し、所定の JSON schema に合致する構造化出力を要求する。

出力後、schema validation を行い、型、enum、最大文字数、配列数、ID 形式などを検査する。

### 15.6 field-level repair

schema validation に成功した場合でも、次のような場合には補完対象とする。

- 登場人物が空である。
- 状況説明が空または汎用的である。
- 構図説明が空または状況説明と同一である。
- 背景が空または現在の場面などの汎用語のみである。
- セリフが必要な場面でセリフもナレーションもない。
- ページ目的や継続性メモが物語の進行を反映していない。

補完は、ページ目的、由来シーン、話本文、登場人物候補、コマ役割から行う。

### 15.7 プロンプト構築

システムは、保存された構造化データを順番に読み出し、画像生成モデル用の第一プロンプトである draft prompt を決定論的に構築する。

draft prompt は以下を明示する。

- 1枚の完成漫画ページとして生成すること
- ページ番号とページ目的
- コマ数と読順
- レイアウト
- 参照画像の役割
- コマごとの状況
- コマごとの登場人物と外見参照
- コマごとの構図、カメラ、背景
- セリフ、話者、ナレーション種別
- 画風制約
- 禁止事項

### 15.8 Prompt compiler

draft prompt または compiler brief を LLM に渡し、画像生成モデルが解釈しやすい自然言語の第二プロンプトである compiled prompt へ整形する。

ただし、LLM による整形は補助であり、必須情報を落とした場合には採用しない。

### 15.9 Lock 検査

コンパイル後のプロンプトについて、少なくとも以下を検査する。

- Dialogue lock が残っているか。
- Visual lock が残っているか。
- 各コマの順番が残っているか。
- 必要な登場人物名が残っているか。
- セリフ文面が残っているか。

欠落した場合、第二プロンプトである compiled prompt を破棄し、第一プロンプトである draft prompt 又は補完後プロンプトを採用する。

### 15.10 画像生成

システムは、最終プロンプトと参照画像を画像生成モデルへ渡す。

ページはコマ単位ではなく、ページ単位の完成画像として生成される。

再生成の場合も、既存生成画像を編集対象として扱うのではなく、現在保存されている入力内容から新規作成する。

## 16. 変形例

本発明は以下の変形を含み得る。

- 画像生成モデルは任意のモデルでよい。
- LLM は OpenAI、Anthropic、ローカルモデル、その他任意の言語モデルでよい。
- structured output は JSON 以外の形式でもよい。
- 参照画像はキャラクター画像、物体画像、背景画像、スタイル画像、レイアウト画像でもよい。
- コマ割りはテンプレートでも、ユーザー編集によるカスタムレイアウトでもよい。
- セリフは画像に焼き込んでも、後から吹き出しレイヤーで配置してもよい。
- 日本語、英語、その他の言語に対応できる。
- 品質検査・補完は LLM、ルールベース、またはその組み合わせで実行できる。
- 出力先は画像生成モデルに限らず、漫画編集ソフト、印刷用 PDF、電子書籍形式でもよい。

## 17. 出願戦略メモ

### 17.1 狙う範囲

主目的は、Lyra の中核である以下のパイプラインをある程度守ること。

```text
story -> page -> panel -> structured fields -> constraint block -> prompt -> compiled prompt check -> image
```

特に守りたいのは以下。

- 物語を指定ページ数へ分配する。
- ページをコマに分割する。
- コマごとの登場人物、構図、カメラ、背景、セリフ、話者を構造化する。
- キャラクター別名を正規 ID に対応付ける。
- 参照画像と構造化コマ情報を統合して画像生成プロンプトを作る。
- 欠落を検査・補完する。
- dialogue lock / visual lock でコンパイル後の情報欠落を防ぐ。
- 第一プロンプトを LLM で第二プロンプトへ整形した後、必須制約ブロックの保持を検査する。
- 欠落時に第二プロンプトを採用せず、第一プロンプト又は補完後プロンプトへ fallback する。

### 17.2 三層の請求項戦略

第1層: 広め

- 物語情報から漫画ページ生成用の構造化データを生成し、画像生成用プロンプトへ変換するシステム。
- 先行技術により攻撃されやすいため、単独の本命にはしない。

第2層: 中核

- ページ分配、コマ分割、entity alias 正規化、参照画像対応付け、field-level repair を含むシステム。
- Lyra の制作フローをある程度守る層。

第3層: 本命

- Dialogue lock / Visual lock を含む必須制約ブロックを生成する。
- 必須制約ブロックを含む第一プロンプトを決定論的に生成する。
- 第一プロンプトを LLM で第二プロンプトへ整形する。
- 第二プロンプトにおける必須制約の欠落を検査する。
- 欠落時に第一プロンプト又は補完後プロンプトへ fallback する。

## 22. 自力出願用の短い説明

Lyra は、ユーザーが入力した物語とキャラクター情報から、漫画ページを生成する Web アプリケーションです。本発明の中核は、物語をそのまま画像生成 AI に渡すのではなく、物語を指定ページ数へ分配し、各ページを複数コマへ分割し、各コマについて登場人物、状況、背景、構図、カメラアングル、セリフ、話者を含む編集可能な構造化データを生成する点にあります。

さらに、キャラクター名や別名を正規のキャラクター ID に対応付け、キャラクター参照画像とコマ単位情報を組み合わせて画像生成モデル用プロンプトを生成します。LLM の構造化出力が形式上正しくても内容が不足する場合があるため、ページ数、コマ数、登場人物、構図、カメラ、背景、セリフ、話者などを検査し、不足項目を項目単位で補完します。

特に権利化したいのは、LLM と画像生成モデルの間に置かれる制御機構です。システムは、セリフの話者や文面を保持する Dialogue lock と、コマごとの登場人物、ショット、角度、背景を保持する Visual lock を含む必須制約ブロックを生成します。そして、これを含む第一プロンプトを決定論的に作成し、必要に応じて LLM により自然言語の第二プロンプトへ整形します。整形後の第二プロンプトに必須制約ブロックの情報が保持されているかを検査し、欠落がある場合は第二プロンプトを採用せず、第一プロンプト又は補完後プロンプトを画像生成モデルへ渡します。

この構成により、ユーザーはプロンプトを書かずに、物語から編集可能な漫画ページ生成用データを作成できます。また、LLM による要約・整形でセリフ話者、登場人物、視覚制約、参照画像対応が失われることを検出できるため、キャラクター一貫性とコマごとの情報整合性を保ったまま画像生成へ進められます。

```text
【課題】言語モデルにより漫画ページ生成用プロンプトを整形する際、コマごとの登場人物、セリフ話者、セリフ文面、参照画像対応、及び視覚制約が欠落又は変形することを抑制する。
【解決手段】漫画ページに含まれる複数のコマのそれぞれについて、登場人物識別子、セリフ文面、セリフ話者識別子、及び視覚制約情報を含むコマ構造化情報を記憶する。コマ構造化情報から必須制約ブロックを生成し、当該必須制約ブロックを含む第一プロンプトを生成する。第一プロンプトを言語モデルにより第二プロンプトへ整形し、第二プロンプトに必須制約ブロックに対応する情報が保持されているかを検査する。欠落がある場合、第二プロンプトに代えて第一プロンプト又は補完後プロンプトを画像生成モデルへ入力する。
【選択図】図5
```

### 23.5 図面として作るべきもの

最低限、以下の5枚を作る。

- 図1: システム全体構成
- 図2: 物語からページ・コマへの変換フロー
- 図3: entity alias 正規化フロー
- 図4: field-level repair フロー
- 図5: 第一/第二プロンプト検査と fallback フロー

図面は、デザイン性よりも処理の対応関係を優先する。

### 23.6 自力出願チェックリスト

提出前に以下を確認する。

- 願書、明細書、特許請求の範囲、要約書、図面の全てを用意したか。
- 請求項で使った用語が明細書に全て説明されているか。
- 請求項1の全構成が実施形態に記載されているか。
- 「検査部」「補完部」「プロンプト切替部」の処理が、入力、処理、判定、出力として書かれているか。
- 先行技術に近い広い主張だけになっていないか。
- 出願前に公開した資料がないか棚卸ししたか。
- 出願日を確保する前に、公式サイトや営業資料で `Dialogue lock`、`Visual lock`、`field-level repair`、`compiled prompt fallback` を公開していないか。
- 出願審査請求は出願日から3年以内に必要であることを管理したか。
- 出願料、審査請求料、減免制度を特許庁の最新情報で確認したか。

### 23.7 費用・期限メモ

確認日: 2026-06-11

特許庁の公開情報上、通常の特許出願では以下を前提に管理する。

- 特許出願料: 14,000円
- 出願審査請求料: 138,000円 + 請求項数 x 4,000円
- 出願審査請求期限: 出願日から3年以内

請求項9項で出す場合の目安:

- 出願料: 14,000円
- 出願審査請求料: 138,000円 + 9 x 4,000円 = 174,000円
- 出願料と審査請求料の合計目安: 188,000円

注意:

- 料金は改定され得るため、提出直前に必ず特許庁の最新料金表を確認する。
- 審査請求をしないと、出願しても審査されない。
- 審査請求期限を過ぎると、原則として特許を取得する道が閉じる。
- 中小企業、スタートアップ、個人等の減免制度に該当する可能性があるため、審査請求前に確認する。
