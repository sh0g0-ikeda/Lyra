# キャラクターの状態変化

## 1. 利用体験とデータの境界

既存キャラを開く →「状態を追加」→ 名称（例: 外傷）と自由入力（例: 左頬に傷、服の右肩が破れている）→ デフォルトの確定画像を参照してpreview生成 → 選択/確定 → `名前・外傷` として選択可能にする。

本名のEntityを複製せず、既存 `entity_states.entity_id` で同じ人物の派生を保存する。表示名は `entity.name + '・' + state.name` から算出する。APIでもこの表示名を返す。本名変更時は追従する。defaultは従来どおり本名。状態名をプロンプト内で別人の固有名として解釈させない。

年齢・衣装・髪・表情・負傷など自由入力を許容する。名前以外の一律固定リストに限定しない。人外も同じ状態基盤を利用できる。元の顔/種族/同一性は維持し、指示された特徴だけ変更する。複合状態（衣装変更+外傷）は1つの確定画像として作る。画像の自動合成や状態の暗黙stackは初期版に含めない。

## 2. 既存再利用と最小migration

`entity_states` は既に `entity_id`, nullable `scene_id`, costume/condition/hair/expression等のnotes、`costume_ref_id`, `extra` を持つ。`panel_entity_assignments` は `state_id` を持つ。これらを置換しない。

追加する列案（次の空きmigration番号を実装時に決定）:

| 列 | 型・互換default | 意味 |
|---|---|---|
| `name` | nullable text | 新規状態名。trim後1–100文字 |
| `description` | nullable text | 新規派生の自由入力。1–2000文字 |
| `reference_image` | nullable jsonb | 現在確定した状態画像descriptor。未確定はnull |
| `updated_at` | timestamptz、既存時刻から安全に初期化 | 同時編集検出。fingerprintは内容も含める |

新規派生APIはname/description必須。既存note-only stateはnullのまま存続し、表示だけ `状態 {短い識別子}` 等にfallback。既存notesを破壊的に新自由入力へ変換しない。新規派生はdescription非nullを識別条件とし、以後nullへ戻せない。旧CRUDの省略で新列を消さない。移行済みnote-onlyを派生にする場合は明示的な変換/preview確定を必要とする。

descriptorは内部専用のbounded schema: `ref_id`, `s3_key`, `storage_owner_user_id`, `image_model`, `base_ref_id`, `created_at`, `input_fingerprint`。画像bytes/base64はDBに入れない。候補は既存temp保管、確定でsavedへ昇格。1状態につき現在の確定画像1枚を基本とする。置換後の古いキーを即時削除しない。

### 既定のreference_setsへ混ぜない理由

既存base画像一覧へ状態画像を無印appendすると、base primary選択・ready判定・旧UI・serializerへ混入する。これを防ぐための大規模修正より、既存stateへの画像descriptor1列追加の方が影響が小さい。**状態確認で `reference_sets.primary_ref_id` を絶対に更新しない。** 画像保管/候補署名/認証済み配信/生成job/精算の仕組みは再利用する。

legacy `costume_ref_id` は既存意味で残す。新variantの確定画像と同じ物として二重書込みしない。既存note-onlyを急に画像必須にして旧ページを止めない。

## 3. APIと生成job

既存scene state APIは残す。再利用可能な派生は `scene_id=null` を基本とし、シーンへの関連があっても、それだけで「ここから必ず継続」と意味変更しない。

追加API案:

- `GET/POST /entities/:entity_id/states`: 同じworkの状態一覧/派生追加。
- `PATCH /entities/:entity_id/states/:state_id`: 名称・自由入力編集。既存のlegacy更新経路とは互換にする。
- `POST /entities/:entity_id/states/:state_id/generate-reference`: optional image_model、quote/revision、idempotency情報でpreview job受付。
- `POST /entities/:entity_id/states/:state_id/reference/confirm`: 署名候補と期待revisionを検証して確定。
- `GET /entities/:entity_id/states/:state_id/reference-image`: 既存認証済み配信形式で画像を取得。

最終のpathは既存route命名に寄せるが、責務を混ぜない。raw S3 key、任意URL、任意の別人画像をconfirm/generateの入力にしない。state IDだけを知っても読めない。個人/active organization membershipと編集/生成権限を独立検証する。

jobは既存 `entity_generate` に追加params: `target:'entity_state'`, `entity_state_id`, `base_primary_ref_id`, `state_input_fingerprint`, `image_model`, `pricing_version`。target省略は旧base生成。entity単位active uniquenessは保ち、baseとstateの同時生成を初期版では直列化する。

既存のsource key policyはtemp/session向けなので、そのallowlistを無条件にsaved全体へ広げない。state専用経路がentity所有・確定primaryを検証し、server-sideで正しいdefault画像を読んでadapterへ渡す。

### 遷移・失敗時

`draft → generating → candidate → confirmed`。失敗/取消はdraftまたは元のconfirmed画像へ戻る。再previewの受付や失敗で既存の確定画像を消さない。新候補の確定まで前の画像を利用できる。自由入力編集後は旧画像が編集後の状態を表すと偽らず「再生成未反映」と表示し、選択可能性をreadinessで判定する。

候補tokenにはuser/tenant/entity/state/job/targetと期限を束縛。base候補や別state候補の流用を拒否する。confirmはstateとbase reference setを一定順でlockし、job時のbase_ref、自由入力fingerprint、state更新時刻、所有・権限を再確認。途中変更は `RESOURCE_STALE` とし、baseや既存確定画像を上書きしない。繰返しconfirmは同じ結果で冪等にする。

新規状態previewはユーザー決定の1回1 credit。production gateは実測・採算判断までOFFとし、通常base preview1の契約も変更しない。credit控除・失敗/取消refundは既存jobの仕組みを通す。名前の編集/状態選択/本文自動入力自体では画像料金を取らない。

## 4. ページ生成との接続

コマassignmentの `state_id=null` はdefault。新variantのIDなら、そのstateの確定 `reference_image` を選ぶ。未確定/壊れた画像/別work/生成入力から変更済みなら生成前にblocker。**外傷画像が無いからdefaultへ黙って戻すことはしない。** legacy note-onlyは従来の注記・参照の意味を保ち、新機能の「確定画像付き状態」とは区別する。

`PageGenerationInputImageBuilder`, readiness, PromptBuilder, generation snapshotを更新する。参照キーはentityだけでなく `(entity_id,state_id,ref_id)`。同じページでdefaultと外傷が共存する場合は両方を送信し、`人物A/既定/参照1`, `人物A/外傷/参照2` とコマ指定を明記する。人物同一性と画像の使い分けを別々に指示する。

参照上限と追加creditsはdistinct画像数で計算する。現行12枚上限を維持し、超過時は受付前blocker。参照を勝手に捨てて費用を下げない。ページsnapshotにstateId/refId/モデル/subjectLabelを追加し、旧snapshotの欠落はdefaultとして読めるようにする。名前・画像・本文の変更で保存済みページ画像を自動更新しない。

## 5. 所有権、削除、保存期間

法人では生成actorとentity作成者が異なる。画像キーのownerは既存storage契約と整合する `storage_owner_user_id` をserverが決めてdescriptorへ保存し、配信/renderer/exportで同じ検証関数を使う。membershipによる認可とS3 key所有者の整合検査を混同しない。URLに人名を入れない。

新state画像を `ImageStorageReferenceRepository` のlive参照列挙と `AccountDeletionRepository` のpersonal asset列挙へ追加する。法人資産をactorの退会で誤削除しない。画像置換時は古いkeyを即時deleteせず、既存のsnapshot/履歴を含む到達可能性と保存期間に従う。利用中stateの削除は既存assignment等を調べConflictにし、勝手にdefaultへ置換しない。未使用draft削除は可能。状態renameはIDを保つ。

現行pruneの列挙だけでは古いsnapshot参照の保持を保証できない。少なくとも保持期間内の `generation_jobs.result.input_snapshot.references[*].s3Key` をprotected keyへ追加し、live state画像と一緒に評価する。snapshot保持期間とjob pruneの順序を合わせる。退会による削除は当該個人のsnapshot保護より優先する一方、他の法人が所有する資産まで消さない。

## 6. 受入条件

元primary不変/旧gallery不変、他entity候補拒否、元画像未確定拒否、生成中の元画像/自由入力変更検出、法人actor違い、同時confirm1回、preview失敗でも旧確定保持、旧job互換、note-only旧state互換、default/外傷混在render、参照数見積、削除保護、退会/prune、日英ラベルをテストする。
