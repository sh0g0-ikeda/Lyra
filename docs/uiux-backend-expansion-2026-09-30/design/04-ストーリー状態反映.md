# ストーリーに沿った状態の自動割当

## 1. 必須の動作

同一人物のdefault → 負傷 → 負傷継続 → 回復を、ページ・コマの読順に沿って反映する。シーン境界だけでは不十分。同じシーン内の途中のコマでも変化できること。

例えばP1コマ1–2はdefault、P1コマ3で負傷し外傷state、P2全コマも同じ外傷state、P3コマ2で回復してdefault。P1の生成ではdefault/外傷の両方の参照が必要になる。負傷を描くコマから変化が見えるか次コマからかは本文と描写計画で決め、その境界を利用者が確認・修正できるようにする。

AIが物語を解釈する工程と、確定境界以降へ同じ状態を伝播する工程を分離する。**物語の意味を決定的なコードだけで判定できるとは主張しない。** 曖昧な推測は警告/確認に回し、継続だけを決定的なresolverで保証する。

## 2. 保存する入力と結果

- 状態ライブラリ: 既存entity_states + 確定画像。単なる `scene_id` 関連を自動的な発効時刻に読み替えない。
- 話の開始状態: 新規 `episodes.starting_entity_states JSONB NOT NULL DEFAULT '[]'` 案。要素は `{entity_id,state_id}`、state_id=nullは明示default。最大100要素か既存entity制限の小さい方、entity重複不可、同work/確定参照検証。空なら全員default。前の話の最終状態を暗黙に継承しない。
- 実際のコマ設定: 既存 `panel_entity_assignments.state_id` に保存。別timeline tableは初期版では作らない。
- 推論の根拠/変化点: 既存generation job resultにbounded `state_transitions` と `state_blockers` を記録。保存したコマ設定の監査用であり、別の競合する正本にはしない。

開始状態の新列は旧API省略で上書きしない。新Mobile/Webの明示操作で保存する。開始状態に画像未確定のvariantは選べない。利用中状態の削除guardはこの列も確認する。

## 3. 全話計画の追加schema

compiled planの内部拡張案:

```ts
type StateTransition = {
  entity_id: string;
  state_id: string | null; // null = defaultへ戻る
  starts_at_panel_id: string;
  source_scene_id: string | null;
  source_field: 'introduction' | 'middle' | 'climax' | 'ending_hook' | 'scene';
  source_quote: string; // 最大300文字の保存本文中の根拠
};
```

最終schemaは既存story構造の正確なfield名へ合わせる。全話で最大512イベント（Domain定数化）、各quote300文字、提案状態名100/説明2000文字を上限案とする。上限超過は切り詰めて採用しない。既存上限内のstructured-output再試行で解消しなければ `LIMIT_EXCEEDED` で全体を失敗させ、transition/assignmentを一切applyしない。

現在のcompiler briefはpanel order中心なので、実在page/panel ID・読順・source_scene_idsと、状態ID/名称/自由入力/画像確定状態を明示して渡す。LLMにS3 key/秘密値は渡さない。画像未確定候補も候補として識別し、確定済みと誤認させない。

イベントはページごとに独立推論せず、全話のbeat計画で一度整合させる。そのイベント表を各chunkへ不変入力として渡す。schema変更前のjobやfeature OFFは旧compiler/planを読めるようversion分岐する。旧jobに新必須fieldを突然要求しない。

## 4. 検証とresolver

1. 保存済みstory・scene・開始状態・確定状態画像一覧と既存page/panelのsnapshotを取得。
2. 全話planと状態変化候補を生成。足りない状態は `unresolved_state_transitions` として名前・自由入力案・根拠・境界を返す。有料画像を自動生成しない。
3. Zod、実在ID、同work/entity、panel読順、同人物同境界の重複、確定画像の実在・入力freshnessを検証。原文quoteは指定fieldの連続部分と一致することを、定めたUnicode/空白正規化の範囲で検査。引用だけで意味が正しいとは判定せず既存内容監査も通す。
4. 本文に無い負傷/年齢変化等、未解決の複合状態、矛盾する戻り/順序、出典が無い推測は保存しない。監査がイベントを修正した場合も同じ検証を再実施する。
5. resolverが開始状態から読順に走査し、イベント開始コマを含めて当該stateへ切替。人物が一時不在でも後の登場に持ち越す。次の明示変化まで維持し、nullイベントでdefaultへ戻す。
6. 既存の手動割当との競合と、入力fingerprintを再確認し、既存の全話transaction内で再検証・保存。全page/panel更新が成功した場合だけcommit。

## 5. 不足・曖昧さ・手動設定

状態が未作成/未確定なら `STATE_REFERENCE_REQUIRED`。必要な候補（例: 外傷）を提示し、利用者が名称・自由入力を確認してpreviewを明示生成/確定した後に再実行する。自動入力は無料、画像previewだけ通常の明示課金。状態が揃えば以降のコマ割当は自動になる。候補が複数で意味が曖昧なら `STATE_MAPPING_AMBIGUOUS` として選択を求める。

既存jobに新しい待機状態を大量追加しない。最小版はjobを安全なerror/blocker結果で終了し、全話の既存設定は変更しない。blockerをjob.resultへ保存するためrepositoryのfail更新とjobs APIのallowlistを明示的に拡張する。raw LLM応答は返さない。

手動のstate割当を無断で消さない。既存assignmentがある話を再自動入力する際は変更対象の確認を行い、`state_assignment_policy:'overwrite_existing'` を明示送信した場合だけ変更/clearを許す。未指定は既存stateを保護し、異なる結果なら `STATE_ASSIGNMENT_CONFLICT` で原子的に失敗。既存には由来の区別がないため、過去の割当を推測でmanual/autoに分類しない。初期版で新provenance列は不要。

利用者がコマで状態を直接上書きできる導線も残す。状態ライブラリを編集しただけで過去の割当・画像は変更しない。「このコマ以降へ適用」をUIに足すなら対象範囲の確認と同じresolver/transactionを使い、無関係な全話を更新しない。

## 6. 競合・保存・rollback

fingerprintへ開始状態、状態のname/description/reference descriptor、base reference revision、本文・scene、page/panel構造、既存assignment、policy、plan versionを含める。state生成/再確認や本文編集があれば古いplanは `RESOURCE_STALE`。

既存 `commit_started_at` とepisode graph lockを維持し、新state画像/開始状態も同じlock順・再読対象へ加える。前回の生成画像を次の画像の暗黙参照にしない。commit途中のcancel/worker retryも既存契約で整合させる。

`EpisodePagePlanApplyResult`、`EpisodeStoryAutofillExecutionRepository` の成功時result組立て/失敗merge、`routes/jobs.ts` の公開allowlist、Mobile API契約まで更新する。現状countsだけのresultでイベント根拠を失わないようテストする。event/quoteは所有者だけが読める。

## 7. 受入条件

変化前default/同一scene途中の負傷/次ページ継続/一時退場後の継続/回復null/二つ目の状態/別人物に波及しない/開始状態/複合状態不足/不明ID/quote不一致/曖昧な事件/同境界重複/順序変更/未確定画像/同時編集/明示上書きの有無をfixture化する。

失敗時は既存全page/panel・画像・credits不変。成功時はID/枚数/コマ数を維持。既存の二段階監査と物語の重要展開を保持する。LLM mockによる単体検証と、許可されたテスト専用本文によるstaging品質評価を分ける。
