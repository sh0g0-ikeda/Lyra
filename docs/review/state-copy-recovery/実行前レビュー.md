## 1. 結論と採用する方針

1. 現行の未確定処理を、経過時間や画像の存在だけで解除する方法は採用しない
2. 現行処理は、元の呼び出しが持つ完全な成功応答か「一度も送信していない」という証拠でのみ解決する。証拠を失った旧処理は個別保留する
3. 今後の新しい処理には、**試行専用の保存先を条件付き書込で占有し、復旧時は同じ保存先を空の保護用オブジェクトで占有し続ける方式**を設計案として採用する
4. この方式は「元の通信が終わった」と推定するのではなく、「遅れて到着する画像を保存できなくした」と証明する。両者を別の状態として記録する
5. 保護用オブジェクトの保持、バージョン消去、権限、費用、実サービス受入を承認・検証してから実装する。自動解除は今回追加しない

安全性に関する設計作業はこの資料で具体化した。ただし、設計完了は機能公開可能という判定ではない。以下の条件を満たす実装と受入は別作業であり、現行候補の実行コード・既定の機能 flag は変更していない。本番の実際の flag 値は未確認。

## 2. 現行契約でできる復旧／できない復旧

現在は job の `state_reference_copies` に exact key、試行 UUID、`unresolved / succeeded / not_dispatched` がある。S3 への要求には試行 UUID が渡らず、保存先も試行ごとの不変オブジェクトではない。外部 request ID と試行 UUID の耐久的な対応記録もない。

| 観測・証拠 | 現行での扱い | 理由 |
|---|---|---|
| 元の呼び出しが単回 copy の完全な成功応答を保持している | 自分の token に限り `succeeded` を記録できる | a847ba1 の別 DB 接続による復旧もこの範囲 |
| 元の呼び出しが copy callback を一度も実行していない | 自分の token に限り `not_dispatched` | admission COMMIT 応答喪失も、証拠を持つ元の処理なら対象 |
| `succeeded` が DB に既に保存されている | 再 copy せず descriptor 保存を再試行 | revision／所有者／退会状態は再検証 |
| SDK が失敗・abort、プロセスが停止、資格情報を無効化した | 保留 | 既に受け付けた外部処理の終了証拠ではない |
| HEAD が404／存在しない | 保留 | 元要求が後から保存する場合と区別できない |
| HEAD が存在／ETag が候補と一致 | 保留 | 以前の同じ内容の画像と、今回の完了を区別できない |
| 新しい再試行が成功 | 元試行は保留 | 先の要求が未完了かもしれない |
| 一定期間イベントやログが来ない | 保留 | 記録設定・遅延・欠落・保存期間を区別できない |
| 外部成功イベントがある | 個別の証拠レビューの入力のみ | 今の DB token と外部 request ID が結び付いていない。自動解除しない |

AWS は copy の HTTP 200 の内部にもエラーがあり得るとして、応答全体の処理を要求する。[CopyObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)
HEAD の403と404は権限によって異なり、削除マーカーが過去の版を隠す場合もある。[HeadObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)

**識別不能性の反例：**「画像なし・ログなし・ローカル処理停止」という同じ観測から、外部書込が一度も受理されなかった場合と、受理済みで遅延している場合の両方が成立する。前者だけを仮定して解除すると、後者では退会後に画像が現れる。追加の確かな証拠なしに両方を安全に解除する手順はない。

## 3. 新しい処理向けの具体的な復旧プロトコル

### 3.1 必須の前提

- 新しい専用 prefix と、ユーザー名・user ID・job ID を含まないランダムな試行 key を使う。既存 key を再利用しない
- この prefix に画像を書ける全ての処理が、保存先に対する `If-None-Match: *` を使用する。コピー元の条件とは別である
- 画像を新規作成する role と marker を置換する recovery role を分け、画像側には If-Match による上書きを許さない。marker の本文が空であることは recovery 実装でも検証し、IAM だけで本文の意味まで保証できるとは扱わない
- 個別試行の token、protocol version、画像の digest、MIME、byte 数、元画像の版を DB へ先に記録する。metadata に個人名・本文・元 key を入れない
- cleanup、Lifecycle、replication、restore、手作業を含め、保護用オブジェクトを削除・上書きする別経路を排除する
- marker が通常オブジェクトとして存在し続ける。S3 の「削除マーカー」では代用しない
- byte 上限付きの読取、所有者、provenance、候補／revision の検証を行う。現在の汎用 `S3StoredImageLoader` は byte 上限がないため、そのまま流用しない

AWS は単一 key の更新の atomicity と、書込・metadata 読取の強い整合性を説明する一方、複数 key 間の atomic 更新は提供しない。以下はそれを前提にした**Lyra 側の設計上の推論**であり、実サービス検証の代わりではない。[S3 consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)

### 3.2 画像書込

1. 認可済みの完了候補から画像を取得する。取得中の失敗は保存を開始した証拠ではない
2. 読取上限、画像 MIME、空／破損、source version または content digest を確認する。上限値は既存の画像規格に照合して実装前に確定する。無制限の buffering は不可
3. user／job lock の下で入力と退会状態を再確認し、新しい token と保存先 key を耐久記録する
4. `PutObject` に、画像、試行 metadata、`If-None-Match: *`、明示的な単回 SDK 設定を付ける
5. 完全な成功応答は同じ試行だけに記録する。失敗／応答喪失は `unresolved` のまま残す。別 key へ無断で再試行しない

最初の実装案は **bounded GET + conditional PutObject** とする。conditional CopyObject は API と SDK には存在するが、AWS の bucket policy の説明には条件付きコピーが501になるという記載が残るため、policy enforcement まで動作すると仮定しない。CopyObject の最適化は、AWS の説明整理と exact policy の staging 受入を通過した場合だけ別途検討する。[Conditional-write policy documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html)

PutObject は成功時にオブジェクト全体が保存され、条件付き作成をサポートする。[PutObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)

### 3.3 未確定試行の復旧

復旧処理は先に DB token／protocol／key／所有者を検証する。外部結果を得た後にも同じ lock と期待状態で再確認する。

| 保存先の状態 | 行う操作 | 確定できること |
|---|---|---|
| 存在しない／未観測 | **同じ key** に空 marker を `If-None-Match: *` で作成する | marker の完全な成功応答、または厳格に一致する marker を再読取できた場合だけ効果を遮断した証拠になる |
| 正しい試行 token と digest の画像がある | 画像の receipt を検証する。採用可能なら descriptor を確定 | 単なる存在ではなく、専用 namespace・書込契約・token 対応を満たす新方式に限る |
| 画像が勝ったが、退会・stale・取消で不要 | `If-Match: 観測した画像ETag` で**空 marker に原子的に置換**する | 画像を削除して空白にする時間を作らず、遅延した追加要求も遮断 |
| 自分の正しい marker がある | 再読取結果を検証し、DB receipt を再保存 | 応答喪失／DB失敗後でも、同じ marker で冪等に復旧できる |
| 412／409 | 勝者を再観測して上記へ戻る | エラーコードだけを成功にしない |
| 403、timeout、違う token、未知 metadata、チェックサム不一致 | 保留・調査 | 安全な成功や未送信とは判断できない |

新しい終端状態は `effects_fenced` とし、`not_dispatched` と混同しない。元要求が送信されたか、通信が終わったかを示す状態ではない。空 marker の完全な証拠と、後述のデータ消去条件が揃って初めて退会を進める。

同じ key の条件付き書込では最初に完了したものが勝ち、後続は前提不成立となる。現在版が削除マーカーなら条件付き作成できてしまうため、普通の空オブジェクトを使う。[Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

### 3.4 消去、保持、複数の復旧処理

- 画像が勝った後の plain `DeleteObject` は禁止。遅延した重複要求が再作成できるため、marker への置換で key の占有を連続させる
- marker 本文は空、metadata は最小限の protocol／ランダム token／種別のみ。既存の `saved/{user}/...` を匿名 marker と呼ばない
- 本当に一度も versioning されていない保存先では、原子的な置換後に画像版は残らないという API 契約を前提とする
- versioning が有効／停止済みなら、現在の普通の marker を保持したまま全ページを列挙し、過去の個人画像版を exact version ID で消去する。未知の版、Object Lock、replica、消去失敗があれば退会完了にしない。現在の key-only deletion adapter では対応できない
- marker を消す安全な上限時間は今の契約にない。期限を発明せず、保持を前提に費用・プライバシーを承認する。設定変更で versioning を無効化する対応はしない
- 複数 worker／再起動は同じ token・同じ key に収束する。CAS の敗者は読取へ戻り、receipt 保存は token と state の compare-and-set にする
- DB receipt の保存に失敗しても marker は消さない。pruning も画像以外の証拠と marker の役割を理解し、DB metadata を先に消さない

versioning 下の key 削除は過去の版の消去とは異なる。[Deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html)
Lifecycle は別経路の処理であり、IAM の削除禁止だけで防御を完成させない。全ての該当規則から marker を除外する必要がある。[S3 bucket policies](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-policies.html)

### 3.5 安全性の説明と限界

不変条件は「消去完了を宣言した後も、その試行 key には普通の marker があり、個人画像版は残っていない」。新規画像要求は key が空でなければ成功しない。marker が常に残り、全 writer が条件に従う限り、通信が後から到着しても画像を復活させられない。

この説明は、無条件 writer、marker の削除／期限切れ、別 key の marker、過去版の放置のいずれかで崩れる。S3 全体、バックアップ、CDN、端末保存を含む法的な完全消去の証明ではなく、この保存要求の遅延効果を抑える設計である。

## 4. 旧処理・既存データの扱い

この方式を既存の未確定 CopyObject に後付けしてはならない。元要求が無条件であれば marker を後から上書きできる。token を metadata に後付けしても、過去の要求との対応を証明しない。

1. 旧候補の発行・確認経路、旧 API／worker、queue、手作業の copy を列挙する。flag OFF だけでは既発行候補の confirm を止めたことにならない
2. 既存 attempt は v1／legacy とし、v2 へ自動変換しない
3. 原試行の確かな証拠を持つものだけ、個別レビューで対象・遷移・消去順序を確定する。人が見たから安全という例外を作らない
4. 過去の退会 receipt の deleted-key checkpoint は、遅延画像より前の削除かもしれない。新方式の完了証拠と混ぜず、production bridge の停止条件を維持する
5. 証拠がない場合は保留のまま責任者へ引き継ぐ。AWS への個別調査が必要なら、送る情報・宛先・費用を承認してから依頼する。今回問い合わせは行っていない

新方式の実装では、opaque key の所有者検証、既存 descriptor／配信 policy、退会清掃、pruner、invariant、旧 client 契約まで一体で更新する。新しい namespace に旧実装を戻す rollback は不可。v2 の受付を止めても、既存 marker と互換 recovery は保持する。

最小構成では新しい queue／Lambda／CloudTrail を必須にしない。ただし GET／PUT／HEAD、保存される marker と版、KMS を使う場合の処理、transfer 経路の料金が発生する。ログを増設する案には、その記録・保存・検索料金も加わる。

見積りは「新規試行数 × 画像 GET＋PUT」「未確定試行数 × HEAD＋marker PUT＋再確認」「退会数 × 置換＋版列挙／消去」「保持 marker 数 × storage 単価」を、実 bucket／class／region／平均 byte 数から作る。現時点で無料や具体的な総額を保証しない。

承認が必要な運用判断：最小限の opaque marker を保持する期間と目的、リンク可能性の管理、保留案件の対応責任、staging 予算、本番の停止時間。marker を永久保持できない方針なら、この方式を採用せず公開を保留する。

## 7. ローカル検証と、その証拠の強さ

同梱 `model.py` は Python 標準ライブラリだけを使用し、ネットワーク・AWS・DB を呼ばない。

- pending な画像要求0〜3件、復旧要求1〜3件、versioning 有効／無効の24条件（初期状態は画像なし）を全状態探索し、消去宣言後に「普通の marker が存在しない」または「画像の現在版／過去版が残る」状態を検出しなかった
- 6つの危険な変形では、全て反例を検出した：無条件 writer、marker期限切れ、version削除マーカー、別 key の記録、画像の plain delete、過去版の放置
- 元の応答喪失・DB書込遅延は、画像効果の到着と receipt 保存の順序を独立に扱う。一定時間後に終了するという仮定は置かない
- JSON に全条件の状態数・遷移数と反例の手順を残した

`sdk-wire-check.mjs` はインストール済み AWS SDK `3.1066.0` に架空の handler／資格情報を注入し、socket を開かず、5項目を検査した。条件付き画像作成、空 marker 作成、If-Match 置換の header／metadata、503時の単回呼出し、明示 maxAttempts が成功。合成 handler 呼出し4回、外部要求0回。

**限界：**有限の抽象モデルであり、S3・IAM を再現する emulator でも数学的な実装全体の証明でもない。CAS は atomic、metadata の所有者対応は正しい、marker は除外設定により消えないという前提を置く。モデルの marker 遷移は「正しい観測＋成功する条件付き書込／再試行」を1ステップへ抽象化しており、古い ETag の衝突や再試行順序そのものは検証していない。実 SDK の header 生成を確認しても、実 bucket policy の互換性・権限・費用・無制限の活性は証明しない。

既存の a847ba1 の2512 backend／926 Mobile等の結果は、現行 fail-closed 実装の証拠であり、未実装の新方式のテスト結果ではない。

## 8. 実装後、公開前に通す受入

1. 原要求を遅延させ marker が先に勝つ。画像は後から保存できず、DB記録が失敗しても marker から同じ token を復旧できる
2. 画像が先に勝つ。退会時の原子的 marker 置換後にも重複した条件付き要求を到着させ、画像が復活しない
3. 403／409／412／timeout、誤 token／誤digest／誤bucket、stale state、退会中、複数 recovery を故障注入する。誤った成功や descriptor 公開がない
4. versioned な場合は全ページの過去版消去、lock／replica／list失敗時の停止を検証する。現在の marker を消さない
5. 無条件 writer、plain DeleteObject、Lifecycle と cleaner の marker 消去を防ぐ設定を検証する。設定変更の伝播時間を推測しない
6. 旧 namespace／旧 client／旧退会 receipt は現状の停止条件を維持し、v2 へ自動変換しない
7. 条件を満たすまで flag OFF。receipt の不明数・marker保全失敗・消去失敗の観測と停止基準を運用者が承認する

staging 案は、専用の合成画像合計1MiB以下、S3要求100回以下、単一の承認済み prefix、外部 model 呼出しなしで最初の試験を行う。これは実行許可や費用保証ではなく、見積りと承認のための上限案。marker を消して試験終了する場合も、保留中の画像要求が残っていないことを試験 harness が正に確認できるものだけに限定する。
