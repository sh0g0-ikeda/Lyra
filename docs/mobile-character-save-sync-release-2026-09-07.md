# キャラ保存・プレビュー修正の作業報告

## 何を作ったか（一言で）

「キャラ情報を保存してからプレビュー生成へ進む」際の状態同期と画像の紐付けを修正したAPK **1.0.6 / 99** を作成しました。

[修正版APKのビルドページ](https://expo.dev/accounts/sh0g0/projects/lyra-mobile/builds/56df57bb-818d-4a4b-8d12-0f0312132d0a)

## なぜそれを作ったか

保存が成功しても、続くプレビュー生成が失敗すると画面が古い保存時刻を使い続け、次の保存が409で拒否されていました。また、新しいキャラの読み込みが完了する前に画像を取り込むと、キャラに紐付いていない候補トークンが作られることを確認しました。組織の候補画像GETには、正しい組織IDを未知項目として拒否するAPI側の不具合もありました。

## 具体的にどういう動きをするか（ユーザー目線で）

- 保存成功時に最新情報を画面へ反映します。その後の画像生成が失敗しても、成功した保存の情報を保持します。
- 一覧の読み込み範囲外にあるキャラも、連続して保存できます。
- 保存中に追加入力した内容と、取り込んだ候補画像を保持します。
- 保存済みキャラの読み込み完了後に画像を取り込めます。取り込み中に別キャラや別作品へ移動した場合、完了した画像を移動先へ誤って適用しません。
- 画像のアップロード機能を維持し、案内は日本語・英語へ対応しています。

今回すでにエラーになった取り込み画像は、キャラとの紐付けがない候補として発行されていました。新APKで保存済みキャラを選び、元画像を取り込み直してください。既存の署名付き候補を画面側で別キャラ用に付け替える処理は行いません。

## 技術的に工夫した点（プログラマー向け）

保存応答をセッション・組織・作品に限定した詳細キャッシュと読み込み済み一覧に即時反映し、遅い応答による巻き戻しを防ぎます。通常保存と生成前の保存を共通化し、編集中のローカル差分は保存時のスナップショットと分けて扱います。画像の取り込み開始時にキャラIDと編集対象を固定し、非同期処理の完了時に再確認します。

本番API修正は、AWSで稼働中だった `dda4fda` を基点とする独立ブランチで実装しました。稼働イメージのコンパイル済みルート1ファイルだけを差し替え、API130を2026-09-07 23:15 JSTに反映済みです。2台とも新イメージで起動し、ALB healthy、healthz/readyz 200、反映直後のログに5xx・errorレベルの記録がないことを確認しました。DB・クレジット・トークン検証・worker・シークレットは維持しています。
